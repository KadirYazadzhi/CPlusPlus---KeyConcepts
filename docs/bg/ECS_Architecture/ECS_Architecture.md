# ECS (Entity Component System) в C++ - Пълно техническо ръководство

## 1. Въведение: Краят на Дълбоките Йерархии

В традиционното обектно-ориентирано програмиране (ООП) за игри и симулации, ние използваме дълбоко наследяване.
*   Пример: `Orc` -> `Enemy` -> `Character` -> `GameObject`.
*   Проблем: Какво правим, ако искаме `Orc`, който не се движи (статичен), но има инвентар? Трябва да пренапишем йерархията. Това води до "Диамантения проблем" и огромни, трудни за поддръжка класове (**God Objects**).

**ECS** е архитектурен модел, който заменя наследяването с **Композиция** и е радикално оптимизиран за кеша на процесора (Data-Oriented Design).

---

## 2. Трите стълба на ECS

### 2.1. Entity (Същност)
В ECS, същността не е обект. Тя е просто **ID** (обикновено `uint32_t`).
*   Тя няма данни.
*   Тя няма методи.
*   Тя служи само като уникален ключ, който свързва различни компоненти.

### 2.2. Component (Компонент)
Компонентът е чиста структура от данни (**POD** - Plain Old Data). Той **не съдържа логика** (методи).
*   `PositionComponent`: `{ float x, y, z; }`
*   `VelocityComponent`: `{ float dx, dy, dz; }`
*   `HealthComponent`: `{ int hp; }`

### 2.3. System (Система)
Системата съдържа **само логика**, без състояние. Тя "избира" всички ентитита, които имат определен набор от компоненти, и ги обработва.
*   `PhysicsSystem`: Взима всички с `Position` И `Velocity` и обновява координатите: `pos += vel * dt`.
*   `RenderSystem`: Взима всички с `Position` И `Mesh` и ги рисува.

## 3. ECS и Кеш Оптимизация (The Performance Edge)

Това е основната причина ECS да е стандарт в гейм индустрията (Unreal Engine Mass, Unity DOTS, Overwatch).

### 3.1. Archetypes (Архитипове)
Вместо да държим компонентите в масив от указатели (лошо за кеша), ECS групира компонентите по техния тип.
Всички ентитита, които имат точно `{Position, Velocity}`, се съхраняват в една "таблица" (Archetype).
*   **Резултат:** `PhysicsSystem` чете паметта линейно. Процесорът зарежда данните в L1 кеша перфектно.

### 3.2. SoA (Structure of Arrays)
Вместо масив от структури (AoS), ECS често използва структура от масиви.
```cpp
// Лошо (AoS):
struct Orc { float x, y; int hp; };
vector<Orc> orcs;

// Добро (SoA / ECS):
vector<float> positions_x;
vector<float> positions_y;
vector<int> hps;
```
Ако системата за движение не се интересува от HP, тя дори не зарежда HP масива в кеша. Това спестява пропускателна способност на паметта.

## 4. Популярни библиотеки в C++

Вместо да пишете ECS от нула (което е сложно), използвайте утвърдени библиотеки:

### 4.1. EnTT (The Standard)
EnTT е "STL-ът на ECS". Тя е header-only, изключително бърза и се използва в Minecraft и стотици други игри.
*   Използва **Sparse Sets** за съхранение, което позволява O(1) добавяне/махане на компоненти и много бърза итерация.

```cpp
entt::registry registry;
auto entity = registry.create();
registry.emplace<Position>(entity, 10.0f, 20.0f);
registry.emplace<Velocity>(entity, 1.0f, 1.0f);

// Система:
auto view = registry.view<Position, Velocity>();
view.each([](auto& pos, auto& vel) {
    pos.x += vel.dx;
    pos.y += vel.dy;
});
```

### 4.2. Flecs
Написана на C (с C++ API), тя е известна с отличните си инструменти за визуализация и лесен query език.

## 5. Паралелизъм (Multithreading)

Тъй като системите в ECS често са независими (напр. AI системата не зависи от Render системата), те могат да се изпълняват паралелно на различни ядра без сложни заключвания (mutexes).
ECS библиотеките често имат вградени `Task Graphs` за автоматично разпределяне на системите по нишките.

## 6. Професионално обобщение

1.  **Композиция:** Можете да създадете нов тип враг, просто като му "залепите" нови компоненти по време на изпълнение.
2.  **Performance:** ECS е единственият начин да симулирате 100,000 единици на екрана при 60 FPS.
3.  **Сложност:** ECS изисква промяна в мисленето. Не е подходящ за малки проекти или UI с дълбока йерархия.
4.  **Data-Oriented:** Мислете първо за данните, после за кода.
