# ECS Архитектура (Entity Component System) - Пълно техническо ръководство

## 1. Въведение: Проблемът на OOP в игрите

Традиционното Обектно-Ориентирано Програмиране (OOP) се проваля при големи, сложни симулации (като игри).
Представете си йерархия: `GameObject -> MovingObject -> Enemy -> Orc -> BossOrc`.
Какво става, ако `BossOrc` трябва да има инвентар (като `Player`), но не е `Player`? Множествено наследяване? Диамантеният проблем? "Спагети" код?

Освен архитектурния хаос, OOP страда от **лоша производителност**. Обектите са пръснати из паметта (Heap fragmentation), което води до **Cache Misses**.

**ECS (Entity Component System)** е архитектурен шаблон, който решава тези проблеми чрез **Data-Oriented Design (DOD)**.

---

## 2. Теория: Data-Oriented Design vs Cache Misses

За да разберете защо ECS е бърз, трябва да разберете процесора.
Процесорът е много по-бърз от RAM паметта. Когато той поиска данни, той зарежда "кеш линия" (64 байта).
*   **OOP:** Ако имате масив от указатели към обекти (`vector<GameObject*>`), всеки обект е на случаен адрес. Зареждането на всеки обект води до Cache Miss (чакане на RAM). Процесорът стои бездеен през 90% от времето.
*   **ECS:** Данните са подредени плътно в масиви (`vector<Position>`). Когато заредите една позиция, процесорът автоматично зарежда следващите 3-4 позиции в кеша. Системите обработват данни линейно, без да скачат из паметта. Това позволява **SIMD** (Single Instruction Multiple Data) оптимизации.

## 3. Трите стълба на ECS

### 3.1. Entities (Същности)
Ентитито не е обект. То е просто **ID** (просто едно цяло число, напр. `uint32_t`).
То няма данни, няма методи. То е просто ключ, който обединява компоненти.
*   Entity 1 = "Играчът"
*   Entity 2 = "Куршум"

### 3.2. Components (Компоненти)
Компонентите са чисти данни (**POD - Plain Old Data**). Те нямат логика (методи).
```cpp
struct Position { float x, y; };
struct Velocity { float dx, dy; };
struct Health { int hp; };
```
*   Entity 1 има: `Position`, `Velocity`, `Health`.
*   Entity 2 има: `Position`, `Velocity` (но няма Health).

### 3.3. Systems (Системи)
Системите съдържат **логиката**. Те не притежават данни, а оперират върху всички ентитита, които имат определен набор от компоненти.

```cpp
class MovementSystem {
    void update(Registry& reg, float dt) {
        // "Дай ми всички, които имат Position И Velocity"
        auto view = reg.view<Position, Velocity>();
        
        for (auto entity : view) {
            auto& pos = view.get<Position>(entity);
            auto& vel = view.get<Velocity>(entity);
            
            pos.x += vel.dx * dt;
            pos.y += vel.dy * dt;
        }
    }
};
```

## 4. Памет и Производителност (Archetypes & Sparse Sets)

Магията на ECS е в подредбата на паметта. Целта е компонентите от един тип да са в плътен масив (`std::vector`).

### 4.1. Sparse Sets (Разредени множества)
Популярен начин за имплементация (напр. в библиотеката **EnTT**).
Всеки тип компонент (напр. `Position`) има собствен масив. Ентити ID-то се ползва като индекс.
Но тъй като не всички ентитита имат `Position`, масивът би бил пълен с дупки (Sparse).
Решението е Sparse Set: два масива (Dense и Sparse).
*   **Dense:** Пази самите компоненти, плътно наредени.
*   **Sparse:** Пази индекса в Dense масива за всяко Entity ID.
Това позволява O(1) достъп и перфектна итерация.

### 4.2. Archetypes (Архитипи)
Използва се в **Unity ECS (DOTS)** и **Flecs**.
Ентититата се групират според комбинацията от компоненти, които имат.
*   Всички, които имат `{Pos, Vel}`, са в една таблица (Chunk).
*   Всички с `{Pos, Vel, Health}` са в друга таблица.
Това прави итерацията възможно най-бърза (линейна памет), но добавянето/махането на компонент е по-бавно (мести ентитито в друга таблица).

## 5. Многонишковост и Job System

Тъй като системите са независими и декларират данните, които ползват, ECS позволява лесен паралелизъм.
Ако `MovementSystem` чете `Position` и пише във `Velocity`, а `RenderSystem` само чете `Position`, енджинът може да ги пусне паралелно (ако не си пречат).
Много ECS рамки идват с вграден **Graph Scheduler**, който автоматично разпределя системите по ядрата на процесора.

---

## 6. Предимства на ECS

1.  **Cache Locality:** Системите четат данни линейно от RAM. Това е 50-100 пъти по-бързо от скачането по пойнтъри в OOP.
2.  **Composition over Inheritance:** Можете да направите всяко ентити да прави всичко, просто като му "залепите" компонент. Искате летяща стена? Добавете `FlyingComponent` на стената. Няма нужда от нови класове.
3.  **Refactoring:** Логиката е отделена от данните. Лесно е да добавите нова система, без да пипате стария код.

---

## 7. Професионално обобщение

ECS е стандартът за модерни гейм енджини (Unity DOTS, Unreal Mass, Bevy, Godot). Дори да не пишете игри, концепцията за **Data-Oriented Design** (разделяне на данните от логиката и оптимизация за кеша) е приложима във високочестотна търговия (HFT) и симулации.

Най-добрата C++ библиотека за ECS в момента е **EnTT**. Тя е header-only, изключително бърза и се ползва в Minecraft (за някои части).
