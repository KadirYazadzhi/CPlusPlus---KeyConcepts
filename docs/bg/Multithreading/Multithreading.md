# Мултитърединг (Multithreading) в C++ - Пълно техническо ръководство

## 1. Въведение: Ерата на Паралелизма

Законът на Мур (за увеличаване на честотата на процесорите) умря около 2005 г. Оттогава процесорите не стават по-бързи, а стават **по-широки** (повече ядра). За да бъде вашият софтуер бърз днес, той трябва да прави много неща едновременно.

C++11 направи революция, вкарвайки нишките (`std::thread`), мутексите и атомиците директно в стандарта, елиминирайки нуждата от POSIX Threads (pthreads) или Windows API. C++17 и C++20 надградиха това с паралелни алгоритми, бариери и корутини.

## 2. Управление на Нишки (`std::thread` и `std::jthread`)

### 2.1. Класическият `std::thread` (C++11)
Нишката започва изпълнение веднага при създаването на обекта.

```cpp
void worker(int id, std::string name) { /* ... */ }

int main() {
    int localState = 42;
    // Аргументите се копират (pass-by-value) по подразбиране за безопасност!
    // Ако искате референция, ползвайте std::ref(localState).
    std::thread t(worker, 1, "Builder");

    // КРИТИЧНО: Трябва да извикате join() или detach() преди деструктора на t.
    if (t.joinable()) {
        t.join(); // Чакаме нишката да свърши
    }
} // Ако t се унищожи без join/detach -> std::terminate() (Краш!)
```

### 2.2. Модерният `std::jthread` (C++20)
`jthread` (Joining Thread) е RAII обвивка, която решава проблема със забравения `join()`.
1.  В деструктора си автоматично вика `request_stop()` и `join()`.
2.  Поддържа **Cooperative Interruption** (Стоп токени).

```cpp
void interruptible_worker(std::stop_token stoken) {
    while (!stoken.stop_requested()) {
        // Работи...
        std::this_thread::sleep_for(std::chrono::ms(100));
    }
}

int main() {
    std::jthread t(interruptible_worker);
    std::this_thread::sleep_for(std::chrono::seconds(1));
    // t.destructor автоматично казва "спри" и чака нишката.
}
```

## 3. Синхронизация и Data Races

**Data Race** е ситуация, в която две нишки достъпват една памет едновременно, поне една пише, и няма синхронизация. Това е **Undefined Behavior**.

### 3.1. Mutex (Mutual Exclusion)
Мутексът е най-простият механизъм за защита.
**Златно правило:** Никога не управлявайте мутекси ръчно (`lock/unlock`). Използвайте RAII гардове.

```cpp
std::mutex mtx;
int shared_data = 0;

void safe_increment() {
    // C++17: scoped_lock може да заключи НЯКОЛКО мутекса без deadlock
    std::scoped_lock lock(mtx); 
    shared_data++;
}
```

### 3.2. Shared Mutex (Read-Write Lock) (C++17)
Ако имате данни, които се четат често, но се пишат рядко, `std::mutex` е бавен (защото спира и четците).
`std::shared_mutex` позволява:
*   Множество четци едновременно (`lock_shared`).
*   Само един писател (`lock`), който блокира всички.

### 3.3. `std::call_once` (Singleton Init)
Как да инициализираме нещо само веднъж, безопасно?

```cpp
std::once_flag flag;
void init() { cout << "Init"; }

void worker() {
    std::call_once(flag, init);
}
```

## 4. Локална памет за нишката (`thread_local`)

Понякога не искате синхронизация, а искате всяка нишка да има свое собствено копие на променливата.

```cpp
// Всяка нишка има свой собствен брояч
thread_local int calls_count = 0; 

void func() {
    calls_count++; // Няма нужда от мутекс!
}
```
Това е много полезно за оптимизация (напр. всеки worker thread има свой собствен random number generator, за да не се заключва глобален).

## 5. Проблемът "False Sharing" (Лъжливо споделяне)

Това е убиец на производителността, който не се вижда в кода.
Кешът на процесора работи с "кеш линии" (обикновено 64 байта).
Ако две променливи `A` и `B` са съседни в паметта, те попадат в една кеш линия.
*   Ядро 1 пише в `A`. Това инвалидира цялата кеш линия.
*   Ядро 2 иска да чете `B`. Трябва да презареди цялата линия от RAM, въпреки че `B` не е променено логически.
Резултатът е драстично забавяне ("Ping-ponging").

**Решение:**
```cpp
struct alignas(64) ProtectedData {
    std::atomic<int> counter;
    // Компилаторът добавя padding до 64 байта
};
```

## 6. Атомици и Memory Ordering (Дълбоко гмуркане)

`std::atomic<T>` позволява безопасен достъп без мутекси. Но каква е цената?

### 6.1. Sequential Consistency (`memory_order_seq_cst`)
Това е режимът по подразбиране. Той гарантира, че всички нишки виждат промените в **един и същи ред**. Това е най-безопасно, но най-бавно (пречи на хардуерните оптимизации).

### 6.2. Acquire / Release
Използва се за синхронизация двойка производител-потребител.
*   **Release (Store):** "Всички мои писания преди тази точка трябва да са видими за този, който направи Acquire."
*   **Acquire (Load):** "Искам да видя всичко, което беше записано преди съответния Release."

### 6.3. Relaxed (`memory_order_relaxed`)
Гарантира само атомарност на самата инструкция, но не и ред. Може да видите стойностите "от бъдещето" или разбъркани. Ползва се само за прости броячи (statistics counters).

## 7. Бариери и Латчове (C++20 Synchronization)

C++20 добави мощни примитиви за координация.

### 7.1. `std::latch` (Резе)
Еднократна бариера. Полезна за изчакване на N нишки да се инициализират.
```cpp
std::latch start_signal(3); // Чакаме 3 работника

void worker() {
    // Подготовка...
    start_signal.arrive_and_wait(); // Намалява брояча и чака
    // Всички тръгват едновременно оттук!
}
```

### 7.2. `std::barrier`
Многократна бариера. Нишките се чакат на етапи (Phase 1, Phase 2...). Полезна за симулации и гейм луупове.

## 8. Асинхронно програмиране: `std::future` и `std::async`

Не винаги трябва да създаваме нишки. Понякога искаме просто резултат.

```cpp
// std::async решава дали да пусне нова нишка или да ползва Thread Pool
std::future<int> f = std::async(std::launch::async, []{ 
    return calculate_pi(); 
});

// ... вършим друга работа ...

int pi = f.get(); // Блокира, ако още не е готово
```

**Внимание:** Деструкторът на `std::future`, върнат от `std::async`, е **блокиращ**! Това е известен дизайн дефект в стандарта, който често изненадва програмистите.

## 9. Професионално обобщение

1.  **Thread Pools:** Създаването на нишка е скъпо (OS syscall, stack allocation). В реални приложения не правете `new std::thread` за всяка заявка. Използвайте Thread Pool.
2.  **Lock Hierarchy:** За да избегнете Deadlock, винаги заключвайте мутексите в един и същи глобален ред (напр. винаги A преди B).
3.  **Immutability:** Най-добрата синхронизация е липсата на синхронизация. Копирайте данните, вместо да ги споделяте. `const` данните могат да се четат от милион нишки безопасно.
4.  **Debugging:** Дебъгването на Race Conditions е кошмар. Инструменти като **ThreadSanitizer (TSan)** са задължителни.
