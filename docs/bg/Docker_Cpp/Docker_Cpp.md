# Docker и Контейнеризация за C++ - Пълно техническо ръководство

## 1. Въведение: "Но на моята машина работи!"

В света на C++, една програма зависи от десетки неща: версия на компилатора (GCC 9 vs 11), версия на стандартната библиотека (glibc), инсталирани системни пакети (OpenSSL, Boost) и променливи на средата.
Когато пратите бинарния файл на колега или го качите на сървър, той често гърми с "GLIBC_2.29 not found".

**Docker** решава този проблем, като опакова приложението и цялата му среда (dependencies + OS filesystem) в един изолиран, неизменим **контейнер**.

---

## 2. Docker за C++: Специфични предизвикателства

За разлика от езици с виртуални машини (Java/Python), C++ се компилира до нативен код.
1.  **Архитектура:** Контейнер, билдван на x86 (Intel), няма да тръгне на ARM (Apple M1/M2/Raspberry Pi) без емулация (QEMU), която е бавна.
2.  **Размер на имиджа:** Сорс кодът, хедърите и компилаторът (GCC/Clang) са тежки (стотици MB). Продакшън имиджът не трябва да ги съдържа.

---

## 3. Multi-stage Build: Професионалният подход

Това е стандартът за C++. Използваме един "дебел" имидж за компилация и един "слаб" имидж за изпълнение.

**Dockerfile (Оптимизиран):**
```dockerfile
# --- Stage 1: Build ---
FROM ubuntu:22.04 AS builder

# Инсталиране на компилатор и CMake
RUN apt-get update && apt-get install -y \
    build-essential \
    cmake \
    git \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# Оптимизация на кеша: Копираме само CMakeLists първо!
# Така Docker ще кешира свалянето на библиотеки, ако не сме променили кода.
COPY CMakeLists.txt .
# (Тук може да пуснете cmake, за да свали dependencies)

COPY . .
RUN mkdir build && cd build && \
    cmake .. -DCMAKE_BUILD_TYPE=Release && \
    make -j$(nproc)

# --- Stage 2: Runtime ---
# Използваме "distroless" или slim версия
FROM ubuntu:22.04 

# Създаваме потребител (Security best practice)
RUN useradd -m cppuser
USER cppuser

WORKDIR /app
# Копираме САМО бинарния файл от Stage 1
COPY --from=builder /app/build/my_game_server .

# Копираме и динамични библиотеки, ако не са статично линкнати!
# (За статично линкване ползвайте Alpine Linux и musl libc)

CMD ["./my_game_server"]
```

## 4. Разработка вътре в контейнер (Dev Containers)

Вместо да инсталирате CMake, Conan, LLVM, Python и 50 библиотеки на вашия локален Windows/macOS, можете да ги инсталирате **веднъж** в Docker контейнер.

*   **VS Code Dev Containers:** Позволява ви да отворите папка в Docker и да пишете код там.
    *   IntelliSense работи вътре в контейнера.
    *   Всички колеги в екипа имат **абсолютно една и съща** среда (compiler version, formatter settings).
    *   При `git clone` на нов човек, той просто натиска "Reopen in Container" и е готов за работа за 5 минути.

## 5. CI/CD и Автоматизирани тестове

Docker е гръбнакът на съвременната автоматизация (GitHub Actions, GitLab CI).

1.  Програмистът прави `git push`.
2.  CI системата стартира Docker контейнер (с вече инсталирани инструменти).
3.  Кодът се компилира и се пускат **Unit тестовете**.
4.  Пускат се **Sanitizers** (AddressSanitizer, ThreadSanitizer) в контейнера за откриване на memory leaks.
5.  Ако всичко е наред, Docker билдва финалния имидж и го качва в Docker Hub.

---

## 6. Професионални съвети

1.  **Static Linking:** Ако билдвате статично (`-static`), можете да използвате имиджа `FROM scratch` (0 байта!). Вашият контейнер ще съдържа само вашия binary файл.
2.  **Caching:** Подреждайте командите в Dockerfile от най-рядко променящите се (инсталация на OS пакети) към най-често променящите се (копиране на сорс кода).
3.  **Cross-Compilation:** Използвайте `dockcross` имиджи за лесна компилация за ARM/Android/Windows от Linux машина.

---

## 7. Професионално обобщение

*   Docker премахва "it works on my machine" проблема завинаги.
*   Винаги използвайте **Multi-stage builds** за малки и сигурни имиджи.
*   Не пускайте контейнерите като `root` в продукция.
*   Docker е най-добрият приятел на C++ билдовете, защото изолира сложните системни зависимости.
