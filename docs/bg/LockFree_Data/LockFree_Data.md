# Lock-free структури от данни в C++ - Пълно техническо ръководство

## 1. Въведение: Проблемът с Мутексите

В многонишковото програмиране стандартният начин за защита на данни е `std::mutex`. Мутексите обаче са "песимистични" – те предполагат конфликт и спират нишката.
Проблемите са сериозни:
*   **Blocking:** Нишката спира и чака, губейки процесорно време в context switch.
*   **Priority Inversion:** Нишка с нисък приоритет може да държи мутекс, блокирайки критична Real-time нишка.
*   **Deadlock:** Риск от вечно блокиране при грешен ред на заключване.

**Lock-free** програмирането позволява на нишките да работят върху една и съща структура **без нито една нишка да бъде принудително спирана** от ОС.

## 2. Сърцето на Lock-free: CAS (Compare-And-Swap)

Всички Lock-free структури разчитат на една специална хардуерна инструкция (атомарна операция): **Compare-And-Swap**.
В C++ тя е достъпна чрез `std::atomic::compare_exchange_weak/strong`.

**Логика:**
*"Прочети паметта на адрес X. Ако стойността там е равна на `Expected`, запиши `NewValue`. Ако не е (значи някой друг я е променил!), върни ми новата стойност и не пиши нищо."*

```cpp
std::atomic<int> head(0);

void push(int new_val) {
    int old_head = head.load();
    // Цикъл до успех (Optimistic Concurrency Control)
    while (!head.compare_exchange_weak(old_head, new_val)) {
        // Ако неуспех: old_head се обновява автоматично с новата стойност
        // и пробваме пак.
    }
}
```

## 3. Имплементация на Lock-free Стек (Treiber Stack)

Ето как изглежда най-простият lock-free контейнер.

```cpp
template<typename T>
class LockFreeStack {
    struct Node { T data; Node* next; };
    std::atomic<Node*> head{nullptr};

public:
    void push(const T& val) {
        Node* newNode = new Node{val, head.load()};
        // CAS Loop:
        while (!head.compare_exchange_weak(newNode->next, newNode)); 
    }

    bool pop(T& result) {
        Node* oldHead = head.load();
        // Трябва да проверим дали стекът не е празен
        while (oldHead && !head.compare_exchange_weak(oldHead, oldHead->next));
        
        if (!oldHead) return false; // Празен
        result = oldHead->data;
        // delete oldHead; // ⚠️ ОПАСНОСТ! Виж ABA проблема.
        return true;
    }
};
```

## 4. Предизвикателството: Управление на паметта (The ABA Problem)

В примера горе с `pop`, ако изтрием `oldHead`, друга нишка може още да го чете (преди нейния CAS).
Още по-лошо е **ABA проблемът**:
1.  Нишка 1 чете върха `A`. Подготвя се да смени `A` -> `B`. Спира за малко.
2.  Нишка 2 маха `A`, маха `B`, после връща `A` обратно (същият адрес в паметта!).
3.  Нишка 1 се събужда. CAS вижда, че върхът е `A` (както е очаквала) и сменя `A` -> `B`.
4.  **Грешка:** `B` отдавна е изтрит! Стекът е счупен.

**Професионални решения (Memory Reclamation):**
*   **Hazard Pointers:** Всяка нишка декларира в глобален масив: *"Аз чета този указател, не го трийте!"*.
*   **Epoch-based Reclamation:** Паметта се трие в "кошове". Кошът се изхвърля само когато всички нишки са преминали в нова "епоха" на изпълнение.
*   **std::shared_ptr (atomic):** C++20 позволява `std::atomic<shared_ptr>`, което решава проблема, но е бавно.

## 5. C++20: Atomic Wait и Notify

Преди C++20, ако чакахте атомик да се промени, трябваше да въртите цикъл (`spinlock`), което хаби 100% CPU.
C++20 добавя метод, подобен на `condition_variable`, но за атомици (използва `futex` на Linux).

```cpp
std::atomic<int> flag = 0;

void worker() {
    flag.wait(0); // Ефективно заспива, докато стойността е 0
    // ...
}

void signal() {
    flag = 1;
    flag.notify_all(); // Събужда работниците
}
```
