# Сериализация на Данни (Data Serialization) в C++ - Пълно техническо ръководство

## 1. Въведение: Проблемът с преноса на данни

В паметта на вашата програма (RAM), данните живеят в сложни структури – обекти с указатели, виртуални таблици, динамични масиви разпръснати в Heap-а. Но когато искате да запишете тези данни във файл ("Save Game") или да ги пратите по мрежата към друг сървър, не можете просто да копирате паметта.

**Сериализацията** (или Marshalling) е процесът на превръщане на тези сложни обекти в линейна последователност от байтове.
**Десериализацията** е обратният процес – възстановяване на обектите от байтовете.

Тъй като C++ е език, фокусиран върху производителността, той не предоставя вградена "магическа" сериализация (като Java или C#), защото тя често е бавна. Вместо това, C++ ви дава пълен контрол да изберете най-ефективния метод.

## 2. Бинарна Сериализация (Raw Binary)

Това е най-ниското ниво – директно копиране на байтовете на структурата.

### 2.1. Пример за POD (Plain Old Data)
```cpp
struct PlayerData {
    int id;
    float health;
    double position[3];
};

// Записване
PlayerData player = {1, 95.5f, {10.0, 20.0, 5.0}};
std::ofstream out("save.dat", std::ios::binary);
out.write(reinterpret_cast<const char*>(&player), sizeof(player));

// Четене
PlayerData loadedPlayer;
std::ifstream in("save.dat", std::ios::binary);
in.read(reinterpret_cast<char*>(&loadedPlayer), sizeof(loadedPlayer));
```

### 2.2. Смъртоносните капани на бинарната сериализация
Този метод е супер бърз, но изключително опасен и чуплив:
1.  **Padding (Подравняване):** Компилаторите добавят празни байтове между полетата за оптимизация. `struct { char a; int b; }` може да е 5 байта, но често е 8 байта. Файл, записан от програма, компилирана с MSVC, може да не се прочете правилно от програма, компилирана с GCC.
2.  **Endianness:** Различните процесори подреждат байтовете на числата различно (Little-Endian vs Big-Endian). Файл от PC (x86 - Little) ще бъде прочетен грешно на стар PowerPC или някои мрежови рутери (Big).
3.  **Указатели:** **НИКОГА** не записвайте структура, съдържаща указатели (`char*`, `std::vector`, `std::string`). Указателят е просто адрес в текущата RAM памет. При рестарт този адрес е безсмислен. Трябва да сериализирате *съдържанието*, към което сочи, а не адреса.

## 3. Текстова Сериализация (JSON, XML, YAML)

Текстовите формати са четими от хора (Human-Readable). Те са стандартът за конфигурационни файлове и уеб API-та.

### 3.1. JSON (JavaScript Object Notation)
JSON е кралят на уеб комуникацията. В C++ най-популярната библиотека е `nlohmann/json`. Тя прави работата с JSON интуитивна като работа със стандартни контейнери.

```cpp
#include <nlohmann/json.hpp>
using json = nlohmann::json;

// Сериализация
json j;
j["name"] = "Artorias";
j["stats"]["hp"] = 5000;
j["inventory"] = { "Greatsword", "Shield", "Potion" };

std::string s = j.dump(4); // 4 интервала отстъп за красота

// Десериализация
auto parsed = json::parse(s);
std::string name = parsed["name"];
int hp = parsed["stats"]["hp"];
```

*   **Предимства:** Човек може да отвори файла и да го редактира. Съвместимост с всеки език.
*   **Недостатъци:** Бавен парсинг (текст към число). Голям обем на файла (заради повтарящи се ключове, кавички, скоби).

## 4. Google Protocol Buffers (Protobuf)

Когато скоростта и обемът са важни (напр. микросървиси, мултиплеър игри), текстът е твърде бавен. Google създават **Protobuf** – бинарен формат, който е:
1.  **Силно типизиран:** Дефинирате схема (`.proto` файл).
2.  **Компактен:** Използва Varint (Variable Integer) кодиране. Числото `5` заема 1 байт, а не 4.
3.  **Обратно съвместим:** Можете да добавяте нови полета, без да чупите старите версии на софтуера.

### 4.1. Workflow с Protobuf
1.  Дефинирате схема `message.proto`:
    ```protobuf
    syntax = "proto3";
    message Person {
      string name = 1;
      int32 id = 2;
      repeated string phones = 3;
    }
    ```
2.  Компилирате с `protoc`, който генерира `message.pb.h` и `message.pb.cc`.
3.  Ползвате генерирания клас в C++:
    ```cpp
    Person p;
    p.set_name("John");
    p.set_id(123);
    p.add_phones("555-0100");
    
    // Сериализация до стринг/файл
    std::string binaryData;
    p.SerializeToString(&binaryData);
    ```

## 5. FlatBuffers: Скорост от ново поколение

Protobuf изисква "парсинг" – данните се четат от файла и се създават C++ обекти в паметта (алокации). За игри и системи с критична латентност (като UI на Facebook/Android), това е бавно.

**FlatBuffers** (също от Google) позволява **Zero-Copy Deserialization**.
Данните са подредени във файла по такъв начин, че са директно достъпни като C++ структури без никакъв парсинг. Просто "мапвате" файла в паметта и четете.

*   **Употреба:** Мобилни игри, мрежови пакети с висока честота.
*   **Цена:** По-сложно API за писане (Builder pattern).

## 6. Версиониране и Миграция на Данни

Един от най-големите проблеми в дългосрочните проекти (особено Save Games) е промяната на формата.
Какво става, когато пуснете Пач 2.0 и добавите ново поле `stamina`, но играчът зарежда сейв от Пач 1.0?

### Стратегия за Версиониране
Винаги записвайте номер на версия в началото на файла.

```cpp
const uint32_t CURRENT_VERSION = 2;

struct Header {
    char magic[4]; // "GAME" - идентификатор
    uint32_t version;
};

void LoadGame(std::ifstream& in) {
    Header h;
    in.read((char*)&h, sizeof(h));
    
    if (h.version == 1) {
        // Зареди стар формат и сложи default стойност за новите полета
        LoadV1(in);
        player.stamina = 100; // Default
    } else if (h.version == 2) {
        LoadV2(in);
    }
}
```

## 7. Сравнителна таблица

| Метод | Скорост (R/W) | Размер | Човешка четимост | Сложност | Употреба |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Raw Binary** | Екстремна | Минимален | Не | Висока (ръчна) | Embedded, вътрешни кешове |
| **JSON** | Бавна | Голям | Да (Отлична) | Ниска | Конфигурации, Web API |
| **XML** | Много бавна | Огромен | Да | Средна | Legacy Enterprise системи |
| **Protobuf** | Много бърза | Малък | Не | Средна | Микросървиси, RPC |
| **FlatBuffers** | Моментална | Малък | Не | Висока | Игри, Real-time системи |

## 8. Професионален съвет

Започнете с **JSON** за всичко, докато не докажете с профилиране, че е тясно място (bottleneck). Той е най-лесен за работа и дебъгване. Преминете към **Protobuf** или **FlatBuffers** само когато имате нужда от скорост или компактност. **Никога** не ползвайте Raw Binary за дългосрочно съхранение на данни, освен ако не сте експерт и нямате строг контрол над хардуера.
