# Secure Coding (Сигурно Програмиране) в C++ - Пълно техническо ръководство

## 1. Въведение: C++ като нож с две остриета

C++ е езикът на инфраструктурата. Браузъри, операционни системи, финансови ядра – всичко е на C++.
Това означава, че C++ е **цел номер 1** за хакерите.
Езикът дава неограничена власт над паметта. В ръцете на експерт, това е ефективност. В ръцете на новак (или дори уморен експерт), това са уязвимости.
Над 70% от CVE (Common Vulnerabilities and Exposures) в продуктите на Microsoft и Google са свързани с паметта (Memory Safety).

## 2. Анатомия на Buffer Overflow (Препълване на буфера)

Най-старата и все още най-опасната атака.

### 2.1. Stack Smashing
Когато локален масив в стека бъде препълнен, излишните данни презаписват съседните променливи и, най-важното, **Return Address** на функцията.
Хакерът може да промени този адрес, така че когато функцията приключи (`ret` инструкция), процесорът да не се върне в `main()`, а да скочи към зловреден код (Shellcode), който хакерът е вкарал в самия буфер.

### 2.2. Защита: The "Safe Stack"
Модерните компилатори предлагат защити:
*   **Stack Canaries (`-fstack-protector`):** Компилаторът слага случайно число ("канарче") между буфера и Return Address. Преди `ret`, проверява дали канарчето е живо. Ако е променено -> `abort()`.
*   **ASLR (Address Space Layout Randomization):** ОС зарежда програмата на случаен адрес всеки път, така че хакерът да не знае къде да скочи.
*   **NX Bit (No-Execute):** Маркира стека като "данни, които не могат да се изпълняват".

Въпреки това, ROP (Return Oriented Programming) атаките могат да заобиколят NX защитата, като използват парчета от вашия собствен код (Gadgets).

## 3. Целочислени уязвимости (Integer Overflows)

Математиката в компютрите не е като в училище. `MAX_INT + 1` не е безкрайност, а голямо отрицателно число (при signed) или 0 (при unsigned).

**Сценарий на атака:**
1.  Хакерът иска да купи 10 артикула по $1000.
2.  Обща цена: $10,000.
3.  Хакерът иска да купи `4,294,967,296` артикула.
4.  При 32-битов `unsigned int`: `4294967296 * 1000` препълва и става малко число (напр. $50).
5.  Проверката `if (user.balance > total_price)` минава успешно.
6.  Потребителят получава милиарди артикули безплатно.

**Решение (C++20/26):**
Използвайте `std::cmp_greater` (от `<utility>`) за безопасни сравнения между signed/unsigned.
В C++26 ще имаме наситена аритметика (`std::add_sat`), която "заковава" резултата на MAX стойността вместо да превърта.

## 4. Инжекции и Валидация на Входа

Принципът **"Zero Trust"**: Всичко, идващо извън вашата програма (файлове, сокети, аргументи, environment variables), е отровно.

### 4.1. Command Injection
```cpp
// УЖАСНО!
std::string cmd = "ls " + user_input;
system(cmd.c_str());
```
Ако user_input е `; rm -rf /`, сървърът ви е изтрит.
**Правило:** Никога не ползвайте `system()`. Ползвайте `execVE` фамилията или библиотеки като `boost::process`, които разделят аргументите.

### 4.2. Path Traversal
Ако приемате име на файл за отваряне, хакерът ще подаде `../../../../etc/shadow`.
**Правило:** Винаги канонизирайте пътя с `std::filesystem::canonical()` и проверявайте дали започва с вашата root директория.

## 5. Сигурна Криптография

Най-честата грешка на програмистите е да се опитват да пишат собствена криптография ("Rolling your own crypto"). **Никога не го правете.**

### 5.1. Случайни числа (RNG)
*   **`rand()`:** Не става за сигурност! Предсказуем е.
*   **`std::mt19937` (Mersenne Twister):** Бърз е, но НЕ е криптографски сигурен (може да се предскаже състоянието му след 624 числа).
*   **`std::random_device`:** Това е правилният избор. Използва хардуерна ентропия (/dev/urandom).

### 5.2. Side-Channel Attacks (Time-based)
Ако сравнявате пароли (хешове) с `memcmp` или `operator==`, вие сте уязвими.
Тези функции връщат `false` веднага щом намерят разлика.
Хакерът може да измери времето за отговор (Timing Attack). Ако отговорът е 1 наносекунда по-бавен, значи първата буква е позната!
**Решение:** Използвайте "Constant Time" функции за сравнение (напр. `CRYPTO_memcmp` от OpenSSL).

## 6. Type Confusion и Casting

### 6.1. C-Style Cast
C-style cast `(Type)val` е брутален. Той може да превърне `int` в `FunctionPointer` и да накара програмата да изпълни данни като код.
Използвайте само C++ cast-ове.

### 6.2. Опасността от `const_cast`
`const_cast` премахва `const` защитата.
```cpp
const int x = 10;
int* p = const_cast<int*>(&x);
*p = 20; // UNDEFINED BEHAVIOR!
```
Компилаторът може да е сложил `x` в Read-Only памет. Този код може да крашне програмата. Хакер може да го ползва, за да модифицира константни конфигурационни флагове.

### 6.3. Опасността от `volatile`
Много програмисти мислят, че `volatile` прави променливата Thread-safe. **ГРЕШКА!**
`volatile` казва на компилатора "не оптимизирай тази променлива". То не гарантира атомарност, нито memory ordering. За нишки ползвайте `std::atomic`.

## 7. Модерни инструменти за сигурност

Сигурността не е само знание, а и инструменти.

1.  **Static Analysis (SAST):** Инструменти като **SonarQube**, **Coverity** или **PVS-Studio** сканират кода за уязвимости (CWE - Common Weakness Enumeration).
2.  **Dynamic Analysis (DAST):** **AddressSanitizer (ASan)** и **UndefinedBehaviorSanitizer (UBSan)** трябва да са включени по време на Fuzzing тестове.
3.  **Fuzzing:** Пуснете **libFuzzer** или **AFL++** срещу вашия парсер. Те ще генерират милиони счупени входове, за да намерят къде програмата гърми.

## 8. Supply Chain Security (Сигурност на веригата за доставки)

Дори вашият код да е перфектен, вашите библиотеки може да не са.
*   **Dependency Hijacking:** Хакер може да публикува злонамерена версия на популярна библиотека.
*   **Outdated Libs:** Използването на стара версия на OpenSSL може да ви направи уязвими към известни експлойти (като Heartbleed).
**Решение:** Използвайте инструменти за "Software Composition Analysis" (SCA) като `OWASP Dependency-Check`.

---

## 9. Професионално обобщение

1.  **Memory Safety:** Използвайте `std::string`, `std::vector` и Smart Pointers. Те елиминират 90% от буферните препълвания и Use-After-Free грешките.
2.  **Least Privilege:** Стартирайте програмата си с минималните нужни права. Не ползвайте `root`/`admin`, ако не е критично.
3.  **Secure by Design:** Не добавяйте сигурност накрая. Проектирайте системата така, че грешките да са невъзможни (напр. силни типове вместо `void*`).
4.  **Dependencies:** Сканирайте библиотеките си за CVE (Dependency Check). `Log4j` показа, че дори най-популярните библиотеки могат да са пробити.
