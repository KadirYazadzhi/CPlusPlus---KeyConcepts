# Сигурно програмиране (Secure Coding) в C++ - Пълно техническо ръководство

## 1. Въведение: Защо C++ е мишена за хакери?

C++ предоставя директен достъп до паметта и висока скорост, но не предлага "предпазна мрежа" (garbage collection, bounds checking по подразбиране). Това прави езика мощен, но и изключително уязвим към атаки, ако програмистът не е дисциплиниран.
Над 70% от пробивите в сигурността на софтуерните гиганти (Microsoft, Google) се дължат на грешки в управлението на паметта в C/C++ код.

---

## 2. Buffer Overflow: Класическият враг

Това е най-известната уязвимост. Случва се, когато записвате повече данни, отколкото масивът може да побере.

### 2.1. Атаката "Stack Smashing"
Хакерите препълват локален масив в стека, за да пренапишат **Return Address** на функцията. Така вместо да се върне в нормалния код, процесорът скача към зловреден код (shellcode), инжектиран от хакера.

### 2.2. Защита (Митигация)
*   **Правило 1:** Никога не използвайте забранените C-функции: `gets`, `strcpy`, `strcat`, `sprintf`. Те не проверяват размера на буфера.
*   **Правило 2:** Използвайте `std::string` и `std::vector`. Те управляват паметта динамично.
*   **Правило 3:** Винаги използвайте `.at()` (който хвърля изключение) или проверявайте размера преди запис с `operator[]`.

```cpp
void risky(const char* input) {
    char buffer[10];
    // strcpy(buffer, input); // ГРЕШКА! Ако input е > 10, хак.
    
    // По-добре:
    strncpy(buffer, input, sizeof(buffer) - 1);
    buffer[sizeof(buffer) - 1] = '\0';
}
```

## 3. Инжекции и Невалидирани данни

Ако вашата програма приема вход от потребителя (напр. име на файл, SQL заявка или команда), тя трябва да го третира като **"отровен"**, докато не бъде валидиран.

### 3.1. Path Traversal
Ако позволите на потребител да отвори файл чрез подадено име, той може да подаде `../../etc/passwd` (Linux) или `..\..\Windows\System32\config\SAM` (Windows), за да прочете системни данни.
**Защита:** Винаги използвайте `std::filesystem::canonical` (C++17), за да разгърнете пътя и проверете дали започва с вашата разрешена директория.

### 3.2. Command Injection
Никога не конструирайте команди за `system()` чрез лепене на стрингове.
`system(("ls " + userInput).c_str());` -> Ако input е `"; rm -rf /"`, изтривате диска.

## 4. Integer Overflows (Целочислено препълване)

Когато добавите 1 към най-голямото възможно число (`unsigned short 65535`), то става 0. Това често води до грешни изчисления на размери на буфери.

```cpp
unsigned short count = 65535;
count++; // Става 0
// Заделяме 0 байта, но копираме данни...
char* buffer = new char[count]; 
```
**Защита:** Използвайте библиотеката `<numeric>` или функции като `std::add_sat` (C++26) за наситена аритметика.

---

## 5. Форматиращи низове (Format String Attack)

Никога не подавайте потребителски вход като първи аргумент на `printf`.
*   **Грешно:** `printf(userInput);`
    *   Хакерът може да подаде `"%x %x %x %x"`, за да прочете стека ви (Memory Leak).
    *   Или `"%n"`, за да пише в паметта.
*   **Правилно:** `printf("%s", userInput);` или `std::print("{}", userInput);`

## 6. Съвременни хардуерни и софтуерни защити

Професионалният инженер трябва да знае как да включи защитите на компилатора:

1.  **ASLR (Address Space Layout Randomization):** ОС мести адресите на стека и heap-а при всяко стартиране.
2.  **DEP / NX (Data Execution Prevention):** Маркира паметта с данни като "неизпълнима". Shellcode-ът не може да тръгне от стека.
3.  **Stack Canaries:** Компилаторът (`-fstack-protector-all`) добавя тайно "магическо число" в стека преди return адреса. Ако препълните буфера, променяте канарчето и програмата се самоубива преди да бъде хакната.

---

## 7. Професионално обобщение

*   **Zero Trust:** Валидирайте всеки байт, идващ от мрежата или файл.
*   **Инструменти:** Пускайте статичен анализ (`clang-tidy`) и динамичен анализ (Sanitizers) в CI/CD пайплайна.
*   **RAII:** Правилното управление на ресурси е най-добрата защита срещу Use-After-Free уязвимости.
*   **Update:** Дръжте библиотеките си (OpenSSL, LibXML) обновени. Старите версии имат известни CVE-та.
