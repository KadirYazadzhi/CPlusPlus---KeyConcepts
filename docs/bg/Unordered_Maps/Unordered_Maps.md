# Неподредени Карти (Unordered Maps) в C++ - Пълно техническо ръководство

## 1. Въведение: Революцията на скоростта

`std::unordered_map` (въведен в C++11) промени начина, по който C++ програмистите работят с големи обеми данни. Докато традиционният `std::map` залага на подредбата и логаритмичната скорост, `std::unordered_map` залага на **екстремната скорост** (константно време O(1)).
Той е реализиран чрез **Хеш таблица (Hash Table)**, което го прави идеалния избор за кеш системи, речници, индекси в бази данни и всякакви сценарии, където търсенето е най-честата операция.

---

## 2. Как работи Хеш таблицата? (Under the Hood)

### 2.1. Хеширане и "Кофи" (Buckets)
Магията на O(1) се случва чрез математика, а не чрез обхождане.
1.  **Input:** Взима се ключът (напр. потребителско име "Admin").
2.  **Hash Function:** Прилага се функция `std::hash`, която превръща низа в голямо цяло число (напр. `1489201849`).
3.  **Mapping:** Това число се разделя по модул на броя на вътрешните "кофи" (buckets).
    *   `Bucket_Index = Hash_Value % Bucket_Count`
4.  **Storage:** Стойността се записва директно в тази кофа.

### 2.2. Колизии (Collisions)
Какво става, ако два различни ключа (напр. "User1" и "User2") попаднат в една и съща кофа?
C++ използва метода **Separate Chaining (Отворено хеширане)**:
*   Всяка "кофа" всъщност е указател към свързан списък.
*   Когато настъпи колизия, новият елемент се добавя в този списък.
*   При търсене, алгоритъмът намира кофата (мигновено) и после линейно претърсва краткия списък вътре.

---

## 3. Производителност: O(1) срещу O(N)

*   **Най-добър/Среден случай:** **O(1)**.
    *   Това се постига, когато хеш функцията е добра и разпределя елементите равномерно. Кофите са къси (0 или 1 елемент).
*   **Най-лош случай (Worst Case):** **O(N)**.
    *   Това се случва, ако хеш функцията е лоша и всички 1 милион елемента попаднат в **една единствена кофа**. Тогава map-ът се превръща в бавен `std::list`.

---

## 4. Управление на Паметта: Load Factor и Rehashing

За разлика от вектора, `unordered_map` има два параметъра за растеж:
1.  **Max Load Factor:** Съотношението `size / bucket_count`. По подразбиране е **1.0**. Това означава, че C++ позволява средно по 1 елемент на кофа.
2.  **Rehashing:** Когато добавите елемент и надвишите Load Factor-а:
    *   Заделя се нов масив с повече кофи (обикновено двойно).
    *   **Всички** елементи се прехешират и местят в новите кофи.
    *   Това е скъпа операция **O(N)**.

**Съвет за професионалисти:**
```cpp
std::unordered_map<int, string> m;
m.reserve(1000000); // Заделя достатъчно кофи предварително.
// Така избягвате многократен Rehash при пълнене.
```

## 5. Изисквания към ключа (Custom Types)

За да използвате свой собствен клас като ключ в `unordered_map`, трябва да научите C++ как да прави две неща:
1.  **Да сравнява за равенство** (`operator==`), за да различава колизиите.
2.  **Да хешира** (специализация на `std::hash`).

```cpp
struct Point { int x, y; };

// 1. Равенство
bool operator==(const Point& a, const Point& b) {
    return a.x == b.x && a.y == b.y;
}

// 2. Хеширане (Injecting into std namespace)
namespace std {
    template <>
    struct hash<Point> {
        size_t operator()(const Point& p) const {
            // Комбиниране на хешове (XOR)
            return hash<int>()(p.x) ^ (hash<int>()(p.y) << 1);
        }
    };
}

std::unordered_map<Point, string> map; // Вече работи!
```

## 6. Сигурност: Hash DoS Attacks

Ако използвате `std::unordered_map` в публичен уеб сървър и четете JSON данни в него, сте уязвими.
Злонамерен хакер може да генерира хиляди ключове, които дават еднакъв хеш ("Hash Collision Attack"). Това ще превърне вашата хеш таблица в списък (O(N)), ще натовари процесора на 100% и ще свали сървъра (Denial of Service).
**Решение:** Използвайте по-сложни, криптографски сигурни хеш функции (напр. SipHash) или libraries като `abseil::flat_hash_map`.

---

## 7. Сравнителен анализ: Map срещу Unordered Map

| Характеристика | `std::map` | `std::unordered_map` |
| :--- | :--- | :--- |
| **Структура** | Red-Black Tree | Hash Table |
| **Скорост (Търсене)** | O(log N) - Гарантирано | O(1) - Средно |
| **Ред** | Сортиран (a-z) | Случаен (Хаотичен) |
| **Памет** | Висока (Node overhead) | По-висока (Buckets + Nodes) |
| **Iterator Invalidation** | Никога (при insert) | Може (при Rehash) |

---

## 8. Професионално обобщение

1.  **Default choice:** Използвайте `unordered_map` за бързодействие (Lookups), освен ако не ви трябва сортировка.
2.  **Reserve:** Винаги ползвайте `reserve()`, ако знаете броя на елементите.
3.  **Memory:** Имайте предвид, че хеш таблицата хаби много памет за празните кофи.
4.  **Enum Keys:** Ако ключът ви е `enum`, по-добре ползвайте обикновен масив или `std::vector` (Direct Mapping), това е O(1) без хеширане.
