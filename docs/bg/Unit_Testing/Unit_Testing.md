# Тестване на Код (Unit Testing) - Пълно техническо ръководство

## 1. Въведение: Повече от просто проверка

Unit Testing (Модулното тестване) е практиката на тестване на най-малките изолирани части от кода (функции, класове) поотделно.
В C++ това е критично, защото езикът няма "safety nets" (като GC или VM). Един бъг в паметта може да остане скрит месеци наред и да се прояви само при специфични условия. Тестовете (особено комбинирани със Sanitizers) откриват тези проблеми рано.

Unit тестовете не са просто QA (Quality Assurance) инструмент. Те са **дизайн инструмент**. Ако един клас е труден за тестване, значи той е зле проектиран (твърде силни зависимости, твърде много отговорности).

---

## 2. Философии на тестването (TDD, BDD)

### 2.1. TDD (Test Driven Development)
При TDD пишете теста **преди** кода. Цикълът е "Red-Green-Refactor".
1.  **Red:** Пишете тест, който се проваля (защото функцията не съществува или е празна).
2.  **Green:** Пишете най-простия възможен код, за да мине теста.
3.  **Refactor:** Почиствате кода, знаейки, че тестът ви пази.

TDD гарантира 100% покритие и води до по-чист API дизайн, защото вие сте "първият клиент" на вашия собствен код.

### 2.2. BDD (Behavior Driven Development)
Фокусът е върху поведението на системата от гледна точка на потребителя ("Given-When-Then").
В C++ това често се реализира чрез frameworks като Catch2, които позволяват BDD синтаксис (`SCENARIO`, `GIVEN`, `WHEN`, `THEN`).

## 3. Google Test (GTest): Индустриалният стандарт

GTest е най-популярната библиотека за C++ тестове. Тя предлага богат набор от макроси (Assertions) и интеграция с CMake.

### 3.1. Основни концепции
*   **ASSERT_***: Ако проверката се провали, тестът спира веднага (Fatal failure). Ползвайте го, когато продължаването няма смисъл (напр. pointer е NULL). Ако продължите, може да крашнете програмата.
*   **EXPECT_***: Ако проверката се провали, тестът маркира грешка, но продължава (Non-fatal failure). Това позволява да видите повече от една грешка наведнъж (напр. грешна стойност и грешен размер).

```cpp
TEST(VectorTest, PushBackIncreasesSize) {
    std::vector<int> v;
    v.push_back(1);
    
    EXPECT_FALSE(v.empty());
    EXPECT_EQ(v.size(), 1);
    EXPECT_EQ(v[0], 1);
}
```

### 3.2. Test Fixtures (Фикстури)
Ако няколко теста имат нужда от еднаква инициализация (напр. създаване на база данни, отваряне на файл), използвайте Fixture клас. GTest създава нова инстанция на класа за всеки `TEST_F`, така че тестовете са изолирани.

```cpp
class DBTest : public ::testing::Test {
protected:
    void SetUp() override { 
        // Изпълнява се преди всеки тест.
        // Тук отваряме връзка, създаваме временни файлове.
        db.connect(); 
    }
    
    void TearDown() override { 
        // Изпълнява се след всеки тест.
        // Тук почистваме, дори ако тестът е фейлнал или хвърлил изключение.
        db.disconnect(); 
    }
    
    Database db;
};

TEST_F(DBTest, QueryReturnsData) { 
    auto res = db.query("SELECT *");
    EXPECT_GT(res.size(), 0);
}
```

## 4. Mocking с Google Mock (GMock)

Един от най-трудните аспекти на тестването е изолацията. Ако тествате клас `OrderProcessor`, който прави плащане през `BankAPI`, вие не искате да правите реални банкови транзакции при всеки тест.
GMock ви позволява да създадете "фалшив" (Mock) обект, който изглежда като `BankAPI`, но вие контролирате поведението му.

```cpp
class MockBank : public IBank {
public:
    MOCK_METHOD(bool, pay, (int amount), (override));
};

TEST(OrderTest, ProcessCallsPay) {
    MockBank bank;
    // Очакваме методът pay да бъде извикан точно веднъж с аргумент 100
    // и да върне true.
    EXPECT_CALL(bank, pay(100)).Times(1).WillOnce(testing::Return(true));
    
    OrderProcessor order(&bank); // Dependency Injection
    order.checkout(100);
}
```

## 5. Property-Based Testing

Unit тестовете проверяват конкретни примери (`add(2, 2) == 4`). Но какво ако бъгът е в `add(2731, 8812)`?
**Property-Based Testing** (напр. с библиотека RapidCheck) е техника, при която вие дефинирате *свойства* (инварианти) на функцията:
*   "За всеки вектор `v`, `reverse(reverse(v))` е равно на `v`".
*   "За всяко `x > 0`, `sqrt(x)` е положително".

Библиотеката автоматично генерира хиляди случайни входове (празни вектори, огромни числа, Unicode стрингове), за да се опита да счупи тези свойства. Ако намери грешка, тя се опитва да "свие" (shrink) входа до най-простия пример, който възпроизвежда бъга.

## 6. Mutation Testing

Как да разберем дали тестовете ни са добри? Чрез **Code Coverage**? Не винаги. Може да имате 100% покритие, но да не проверявате нищо (без assert-и).
**Mutation Testing** (напр. Mull или PITest) е техника, при която инструментът *променя* (мутира) вашия код (напр. сменя `+` с `-`, или `if (a > b)` с `if (true)`).
След всяка мутация се пускат тестовете.
*   Ако тестовете минат (зелено) -> **Лошо!** Тестът не е хванал промяната ("Mutant survived").
*   Ако тестовете паднат (червено) -> **Добро!** Тестът е убил мутанта ("Mutant killed").

## 7. Професионално обобщение

1.  **Интеграция:** Unit тестовете трябва да са част от CI/CD пайплайна. Ако тестовете не минават, не може да се merge-не код.
2.  **Бързина:** Unit тестовете трябва да са мигновени (милисекунди). Ако тестовете ви отнемат 5 минути, програмистите ще спрат да ги пускат локално.
3.  **Тествайте поведение, не имплементация:** Не тествайте private методи. Тествайте само публичния интерфейс. Ако private методите са сложни, може би трябва да бъдат изнесени в отделен клас/функция (Helper class).
