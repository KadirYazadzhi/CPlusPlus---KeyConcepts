# Модули (Modules) в C++20 - Пълно техническо ръководство

## 1. Въведение: Краят на 40-годишното наследство

От създаването си през 70-те, C++ (наследявайки C) разчита на `#include` – механизъм за **чисто текстово копиране**.
Когато напишете `#include <vector>`, препроцесорът копира 10,000+ реда код във вашия файл. Ако имате 100 файла и всеки включва вектора, компилаторът парсва тези 10,000 реда 100 пъти. Това е O(N*M) сложност на компилацията.

**Модулите** са най-голямата промяна във физическата архитектура на C++. Те заменят текстовото вмъкване с логическо зареждане на предварително компилирани бинарни интерфейси.

## 2. Анатомия на Модула

Модулите въвеждат нови файлови разширения (`.ixx` за MSVC, `.cppm` за Clang/GCC) и нови ключови думи.

### 2.1. Primary Module Interface Unit
Това е файлът, който дефинира какво "вижда" светът.

```cpp
// math.cppm
export module math; // 1. Декларация: "Аз съм модул math"

// 2. Експорт на функция (видима за импортиращите)
export int add(int a, int b) {
    return a + b;
}

// 3. Скрита функция (невидима отвън)
// Няма нужда от "static" или анонимни namespace-ове!
int helper() { return 42; } 

export struct Point { int x, y; }; // Експорт на тип
```

### 2.2. Консумация (Client Code)
```cpp
// main.cpp
import math;      // Зарежда бинарния интерфейс (BMI)
import <iostream>; // Стандартната библиотека също става модуларна (C++23)

int main() {
    std::cout << add(1, 2); 
    // helper(); // ГРЕШКА: helper не е експортнат
}
```

## 3. Фрагментация на Модули (Module Partitions)

За големи библиотеки, един файл не стига. Модулите могат да се разделят на "дялове" (Partitions), които започват с `:`.

```cpp
// math_geometry.cppm
export module math:geometry; // Дял "geometry" на модул "math"
export struct Shape { /*...*/ };

// math_algebra.cppm
export module math:algebra;
export int calc() { /*...*/ }

// math.cppm (Основен интерфейс)
export module math;
export import :geometry; // Ре-експортва дяловете
export import :algebra;
```
Потребителят пише само `import math;` и получава всичко.

## 4. Глобален и Частен фрагмент на модула

Понякога имате нужда от "стари" хедъри вътре в модула (напр. `<windows.h>`). Те не трябва да изтичат навън.

```cpp
module; // Global module fragment
#include <cstdio> // Текстово включване (само тук е разрешено)

export module mylog;

export void log(const char* msg) {
    printf("%s", msg); // printf е видим тук, но не и за този, който прави 'import mylog'
}
```

## 5. Предимства за големи системи (The Why)

### 5.1. Скорост на компилация (Performance)
Когато модулът се компилира, той създава **BMI (Binary Module Interface)** файл (`.pcm` / `.ifc`).
*   Всеки `import` просто зарежда този бинарен файл (като Deserialize).
*   Парсването се случва **само веднъж**.
*   В реални проекти (като LLVM или Qt), това намалява времето за билд с **40-80%**.

### 5.2. Изолация (Macro Hygiene)
Макросите `#define`, дефинирани вътре в модул, **НЕ изтичат** навън.
Край на конфликтите, където `windows.h` дефинира `min/max` и чупи `std::min`.

### 5.3. Липса на Header Guards
Няма нужда от `#pragma once` или `#ifndef`. Модулната система гарантира еднократно зареждане.

## 6. Професионално обобщение

1.  **Transition:** Не е нужно да пренаписвате всичко. Можете да смесвате `#include` и `import` в един проект.
2.  **Build Systems:** CMake поддържа модули експериментално от версия 3.26+. Изисква се малко настройка (`FILE_SET CXX_MODULES`).
3.  **Бъдещето:** `import std;` (C++23) е крайната цел – един ред, който дава достъп до целия STL, компилиран за части от секундата.
4.  **ODR Rule:** Модулите не ви спасяват от One Definition Rule, но го правят много по-трудно за нарушаване случайно.
